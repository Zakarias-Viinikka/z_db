# add_new_method_to_wrapper

A GUI for adding one method to z_db's web path.

Adding a command means editing macro_core.rs, worker.js, and db_helper.rs by hand, and nothing enforces that the command names match across the three. This tool takes one pasted method, checks that it compiles, and writes the matching entries into the other two files.

add_new_method.sh at the z_db root builds it and launches it in release.

## What you do

Pick where the method goes in macro_core.rs — a named method or "append to bottom". Paste the method. The tool reads the signature and shows what it understood.

"Check only" writes the method into macro_core.rs, runs the configured check commands, and reverts. "Check and apply" does the same and, if the checks pass and the revert verified, writes the other two files too. "Build everything and check" runs the build-everything command from settings and streams it to the same log.

## How the signature decides everything

A method with an input parameter goes in serializedCommands, one without goes in noInputCommands. The same has-input/has-output pair picks which of the four db_helper.rs sections the fn lands in, and which shape it has.

export_database is the exception — no input, but it still passes an empty Uint8Array. It's hand-written and never generated by this tool.

## The guard

The tool has to write macro_core.rs to check it. Before it does: SHA-256 the file, save the exact bytes to ~/.cache/add_new_method_to_wrapper/macro_core_backup.rs, and write a marker file. After the check: write the bytes back, hash again, compare. A mismatch shows a red banner and skips the apply.

If the process dies mid-check, the marker is still there. On next start, the tool offers to restore from the backup.

## Mock mode

Settings has a "use mock paths" checkbox. On, the four paths point at add_new_method_to_wrapper/mock/. "Populate mock folder" copies the real files there. This is how you poke at the tool without touching real files.

The check still runs in the real workspace, so it compiles the real, unedited macro_core.rs and passes trivially. Mock mode exercises the flow, not the compile.

## Settings

~/.config/add_new_method_to_wrapper/settings.json, written on every change. Four file paths, working directory, check commands, use_mock_paths/mock_root, cache_root, build_everything_command.

Default check: cargo check -p db_wrapper --no-default-features --features testing. That compiles the testing mascot. web_mascot.rs uses different helper macros, so a method can pass here and fail the web build. A web check command is in the list but disabled.

UI state (selected position, pasted text, settings header open) lives in ~/.config/add_new_method_to_wrapper/ui_state.json.

## Check command resolution

A command starting with "cargo " is rewritten to go through local_cargo.sh if one exists at or above the working directory.

## Structure

Three crates. app is the window. every_page_ever is the UI. app_core is everything else, no egui dependency, testable without a window.

## Tests

app_core/tests/ covers scan, edit, precheck, guard, and process-level flows using true/false as the check command.
